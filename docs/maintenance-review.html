13. tmpfiles вместо activation

Текущий activation script уже понятен и идемпотентен для обычных каталогов. Проблемы, которую обязательно лечит tmpfiles, не найдено. Выгода перехода: видно полный список path/mode/owner, меньше повторений install -d, стандартный механизм создания каталогов при загрузке. Название tmpfiles не означает временные данные: постоянные каталоги поддерживаются. Правило d с age - не задает очистку по возрасту. Источники: systemd tmpfiles.d, модуль закрепленного NixOS.

Пример узкой замены только двух строк:

systemd.tmpfiles.rules = [
  "d /home/killeik/selfhost/downloads 0755 killeik users -"
  "d /home/killeik/selfhost/miniflux-postgres 0700 999 999 -"
];

Это не заменяет генерацию случайного excalidash/backend.env. Soularr config создается один раз и затем редактируется приложением; Caddyfile, наоборот, обновляется из Git при каждом activation. Их нельзя превратить в одинаковое правило копирования. Пустой SQLite-файл LaraPaper требует отдельной проверки семантики создания/прав. Рекурсивный chown всех данных не нужен.

Выбор: оставить activation целиком; либо перенести только обычные каталоги, оставив bootstrap в activation. Второй вариант немного короче, но некоторое время придется читать два механизма. Не делать этот рефакторинг только ради самого использования tmpfiles. Если выбирать его, проверить обычный switch, холодную загрузку и владельцев до старта контейнеров.

14. Числовые UID/GID и комментарии

Ошибка прав не подтверждена. Числа здесь являются частью контракта mount с образом, а не случайными NixOS users: PostgreSQL 999:999, LaraPaper 82:82, Excalidash 1001:1001; Forgejo явно получает USER_UID/GID=1001. 1000:100 используется через PUID/PGID или user у нескольких контейнеров. Не следует создавать на хосте пользователей с именами каждого приложения только ради замены чисел: это дополнительная сущность без текущей выгоды.

Короткие комментарии полезны рядом с первыми тремя владельцами: какой образ и какой его пользователь требуют эти права. Комментарий 999 is postgres без привязки к образу быстро устареет при смене variant/tag. Перед написанием такого комментария проверить UID в точном действующем image через getent/id, а не доверять общей таблице из интернета. В этом исследовании image users повторно не проверялись; новых гарантий соответствия чисел нет.

Отдельно проверить users.users.killeik.uid: сейчас Nix явно его не задает, а контейнерные PUID используют 1000. Это важно при чистом восстановлении на новый хост; это повод проверить/зафиксировать существующий UID отдельно, но не менять владельцев сейчас. Выбор: оставить; добавить 3 объясняющих комментария после проверки образов. Общий UID framework не нужен.

18. Grafana socket или TCP

Настоящая сложность socket здесь - граница native service и Docker: bind mount /run/grafana, Unix permissions 0660, after Grafana у Caddy, RuntimeDirectoryPreserve=yes. Последнее сохраняет каталог при остановке, что нужно для bind mount: удаление и пересоздание host directory оставляет контейнер на старом inode. Это не повод удалять preserve как лишнюю настройку. systemd RuntimeDirectoryPreserve.

TCP уберет mount, socket permissions и эту зависимость от inode. Но 127.0.0.1 Caddy - loopback самого Docker-контейнера, не native Grafana. Нужно выбрать достижимый адрес хоста, bind Grafana и firewall. Например, Grafana на отдельном TCP-порту, доступном с selfhost bridge, Caddy проксирует на gateway 172.19.0.1; сейчас этот gateway подтвержден network inspect. Не использовать 3000 одновременно как host Grafana bind и Caddy published port 192.168.1.2:3000:3000: получится конфликт адресов при wildcard bind. Вариант с отдельным 3001 потребует ограничить host INPUT с Docker bridge и проверить недоступность из LAN. Это план миграции, не готовая конфигурация. Docker bridge networking.

Еще вариант - native Caddy: socket остается между двумя host services, исчезает Docker mount, но нужно заменить Cloudflare-enabled image на совместимую native сборку с DNS module и мигрировать Caddy data. Перевод только ради одного socket больше текущей задачи.

Выбор сейчас: сохранить уже работающий socket. TCP имеет смысл, если появляются повторные реальные сбои mount/permissions или принимается общее решение о host endpoints. Тогда проверить рестарты Grafana и Caddy в обоих порядках, reboot, HTTPS route и текущий LAN endpoint 3000.

19. Docker network: что реально есть в текущем NixOS

Есть native OCI option containers.<name>.networks = [ "selfhost" ];. Он превращается в --network=selfhost; создание сети в модуле отсутствует. dependsOn описывает зависимости только от других OCI containers. Проверены oci-containers.nix и docker.nix точного lock revision. Native virtualisation.oci-containers.networks или virtualisation.docker.networks для декларации создания Docker network в этих модулях нет. Нельзя предлагать такой выдуманный option.

Вариант Что исчезает Цена для oggy
Оставить NixOS OCI + oneshot Ничего; сеть уже создается декларативной unit Самый маленький вариант, все остается systemd/Nix
OCI networks вместо extraOptions Одна сырая CLI option Косметика; oneshot и dependencies остаются
Docker Compose Compose сам создает network через networks/ipam Перенос 17 containers и управление их lifecycle, env/mounts, интеграция systemd и Slskd guard
Native NixOS services Docker network не нужна мигрированным приложениям Отдельная миграция каждого сервиса, state paths/users, версии, proxy endpoints; не все приложения имеют нужный модуль/версию

Compose действительно владеет объявленными сетями, но external: true снова требует уже существующую сеть. Источник: Compose networks. Native services полезны, если нужны native lifecycle, packages и host permissions сами по себе. Перенос Grafana/Prometheus уже показывает этот подход; переносить весь stack для удаления 15 строк oneshot невыгодно.

У текущего oneshot есть две реальные границы: inspect || create не сверяет subnet существующей сети, а прямой Requires/After на network есть не у всех ее потребителей (Caddy и Slskd получают его явно/через guard). Гонка не воспроизведена, но при пустом Docker state порядок запуска не гарантирован всеми declarations. Узкая будущая правка - дать каждому selfhost container Requires/After на тот же oneshot, без новых менеджеров. Не удалять и не пересоздавать live network при несовпадении subnet: это отключит stack.

Выбор: оставить oneshot; при желании отдельным diff исправить зависимости. Проверка на пустой сети и reboot нужна в изолированном окружении, без удаления рабочей сети oggy. Compose и native migration - отдельные задачи.

20. Firewall: маленькая очистка или смена backend

На oggy проверены Docker 29.8.2 и iptables v1.8.13 (nf_tables). Суффикс nf_tables означает совместимый iptables frontend, а не автоматически native nftables backend Docker. Текущие правила используют CODEX-EGRESS, INPUT/FORWARD и Docker DOCKER-USER для Slskd; это действующие политики, а не неиспользуемые остатки.

Вариант Выигрыш Что придется проверить/поменять
Оставить iptables, сузить подавление ошибок Меньший diff, остается привычная интеграция DOCKER-USER Отдельно проверять отсутствие цепочки/правила; ошибки добавления правил не скрывать
NixOS nft firewall + Docker iptables backend NixOS INPUT/forward policy описывается nft rules Два взаимодействующих набора правил и порядок hook; текущий shell переписать, риск конфликта forward policy
NixOS и Docker native nftables Собственные таблицы описываются декларативно; меньше shell создания/очистки Переписать обе политики, приоритеты hooks, NAT/forwarding и Slskd limits; DOCKER-USER отсутствует

Native nftables backend появился в Docker 29 и на дату проверки обозначен experimental. Он использует отдельные tables; user rules должны жить в своих tables, а не править таблицы Docker. Accept в одной base chain не отменяет drop в другой. Это больше, чем включить один bool. Docker nftables migration. В текущем NixOS есть networking.nftables.tables.<name>.{family,content} и networking.firewall.extraInputRules/extraForwardRules: nftables module, firewall nft module.

Не отключать Docker iptables в надежде, что NixOS allowedTCPPorts заменит Docker NAT/isolation. Published ports проходят forwarding, и host INPUT allowlist сама по себе не описывает весь их доступ. Docker packet filtering, DOCKER-USER.

Узкий первый вариант: ожидаемую ситуацию "цепочка уже существует" определять отдельной проверкой, а создание/flush/append выполнять с видимыми ошибками. Проверки iptables -C ... || iptables -I ... тоже различают отсутствие правила и сбой не идеально; не заменять их на безусловное insert с дубликатами. Stop cleanup может терпеть уже отсутствующие собственные объекты, но не следует прятать stderr всех операций. Не загружать общий iptables-restore с flush Docker tables.

Выбор: сохранить backend, отдельно улучшить диагностику. Native nftables - отдельная миграция с консольным fallback: SSH доступ, codex DNS+internet, запрет codex -> LAN/host, Caddy published ports, счетчики Slskd connlimit и rate limit, Docker restart, firewall reload, reboot. nft syntax check не доказывает сетевую изоляцию. Сейчас исправность не опровергнута, а миграция ради сокращения shell может увеличить суммарную сложность.

Каждый нужный модуль может импортировать тот же файл в своем let; во вложенном containers.codex.config значение доступно через lexical scope. Если все повторы после пункта 16 окажутся в одном файле, проще один местный let, без нового файла. slskdContainerIp уже вынесен в let - он не проблема. Interface, который встречается один раз, сам по себе выноса не требует. Формат MAC в OpenWrt (cc:b5:...) отличается от MQTT ID; не добавлять преобразователь только ради этой пары.

Ограничение: Caddyfile - статический файл с 10.231.40.2:3773; импорт Nix не изменит его. Сделать его шаблоном возможно, но это еще одна миграция. Не обещать единый источник всех network values, оставив этот literal. Выбор: оставить literals; объединить только реально повторяющиеся значения местными let; либо одна таблица выше для нескольких файлов. Практическая выгода появляется при смене LAN/DNS/устройства, а не от числа constants.

22. Секреты: inventory или sops-nix + age

Текущие механизмы выполняют разные задачи: env нужен приложениям, LoadCredential дает файл сервису, Grafana secret_key читает сама Grafana. Новый storage manager не обязан и не сможет сделать интерфейсы потребителей одинаковыми. Не помещать значения в Nix strings/store.

Полный короткий inventory текущих явно объявленных файлов:

/home/killeik/selfhost/miniflux.env Docker Miniflux DATABASE_URL + YOUTUBE_API_KEY

Это не полный перечень секретов внутри application state: app.ini, Slskd/Soularr configs, T3/Codex auth и прочее сохраняются вместе с каталогами из пункта 15. Старый общий .env удален после проверки действующих declarations. Рабочие env-файлы сохранены.

Вариант A: сохранить файлы как есть, поддерживать этот inventory и проверенную зашифрованную внешнюю копию. Восстановление требует отдельно доставить файлы до старта сервисов, согласовать пары DB password/URL и вернуть права. Для одного хоста это самый короткий operational path, если копия действительно есть.

Вариант B: sops-nix хранит зашифрованный документ в Git, расшифровывает на хосте при activation, управляет paths/owner/mode и restartUnits. Age key или host SSH key должен уже быть доступен; незашифрованные данные не нужно включать в store. Поддерживаются dotenv и binary: можно сохранить нынешние env как цельные файлы вместо создания templating framework. sops-nix README.

Цена B: еще один flake input, .sops.yaml/recipients, начальный перенос, резервирование private age recovery key вне oggy, процедура добавления replacement host и ротации. Новый ключ не расшифрует старый ciphertext; потеря единственного decrypt key при потере сервера означает потерю секретов. Изменение файла также не заменяет пароль внутри уже инициализированной PostgreSQL DB - нужна отдельная согласованная ротация приложения и БД. Backup пользовательского state sops не заменяет.

Выбор: сначала inventory + копия без смены механизма; sops-nix оправдан, если хочется хранить восстановимый encrypted config рядом с Git и готов обслуживать recovery key. Возвращаться к нему при нескольких хостах, частых ручных доставках secrets или регулярных пропусках файлов при restore. Не называть текущие runtime files ошибкой только из-за отсутствия sops.

24. Pins и изменение T3 runtime

Зафиксированный revision/hash обеспечивает воспроизводимый исходник и защиту от неожиданной подмены. Проблема возникает, когда процедура обновления считает nix flake update полным обновлением, а отдельный pin забывает; когда нужен security/compatibility fix или перестает собираться старый источник. Сам возраст pin не доказывает необходимость переписывать пакет. mqtt2prometheus здесь небольшой рабочий Go exporter, менять его только ради даты не нужно.

Его текущие pin points в qingping.nix: rev c324374c71ae1102c450d310e8efbbe8db9cbcb5, source hash, vendorHash. Обновлять их отдельным осмысленным шагом: upstream diff, build, прежние metric names и MQTT password-file mode. Изменение vendorHash требуется только при изменении vendored dependencies. Источник проекта: mqtt2prometheus.

Первоначальный audit описывал Nix-пакет T3 SEA и pin patchelf 0.15.2. Теперь используется другой путь: официальный runtime в user home, native user service, Nix отвечает за nix-ld/зависимости/drop-in/linger. В checkout t3code-nightly.nix удаляется. Поэтому предлагать автоматизацию обновления его version/hash или сохранение patchelf override теперь неактуально. См. точные исходники installer/update и границу live-проверки в t3-runtime.md. Handoff выполнен: работает native user service, endpoint сообщает serverSelfUpdate=boot-service; ID окружения и Codex login сохранены.

Компромисс нового пути: T3 может обновляться штатным updater без Nix rebuild, но nixos-rebuild --rollback больше не выбирает runtime из home. Нужны backup userdata и понимание managed launcher rollback. Nix фиксирует систему, официальный updater - T3; текущую runtime version учитывать отдельно. Node SEA содержит runtime и application payload внутри executable: Node SEA. Не patch-ить его новым patchelf без проверки payload/startup. При официальной установке этот custom patching path исчезает, его поддерживать незачем.

Выбор: сохранить custom pin только для mqtt2prometheus; проверять upstream при плановом обслуживании и менять при полезном изменении. T3 runtime вести по отдельной документированной процедуре, не создавать второй updater timer.

25. selfhost-remote: задокументировать назначение позже

Target содержит disk /dev/sda, interface ens3, QEMU profile, SSH и disko. Это не идентичная удаленная копия oggy stack: selfhost.nix/monitoring.nix туда сейчас не импортированы. Успешная evaluation означает корректность конфигурации, не пригодность к установке на произвольный VPS и не наличие рабочего сервера.

Выбор сейчас: сохранить без расширения и пометить как заготовку будущего target. Позже, когда будет конкретная машина, документировать ее назначение, disk/interface, способ установки, owner доступа и нужные state/secrets. Не запускать disko по шаблонному device и не удалять target только из-за отсутствия текущего применения. Отдельная документация не требует сейчас создавать универсальный multi-host module layer.
